按正文中的**单 QEMU、多 vCPU**方案设计测试，以双核收发包为主场景，`-smp 1` 用于验证基础计数与时钟换算。以下内容是测试方案，尚未进行代码验证。

测试需要分别验证：**指令计数正确、全局时间正确、线程持续推进、业务超时行为正确**。仅观察“软件不再超时”，无法判断是否存在时间停滞或 Timer 失效。

测试前，需要把几项行为明确为验收条件：

| 项目            | 验收条件                                                     |
| --------------- | ------------------------------------------------------------ |
| 滑窗等待        | 因达到 skew 上限而等待的 vCPU **仍属于 active 集合**，继续参与最小进度计算 |
| 主线程调度      | 即使全部 vCPU 都在滑窗等待，主线程仍能独立获得执行机会，更新全局进度并唤醒线程 |
| active 状态切换 | `active、raw_base、logical_base` 的读取必须来自一致的状态，避免新旧基准混用；单独对 `raw_icount` 做 atomic read 无法保证这一点 |
| 滑窗边界        | 若要求严格满足 `local <= global + skew`，执行前需限制剩余指令预算；仅在 TB 结束后检查可能产生越界 |
| Idle Time Warp  | 跳时后，后续指令时间换算必须承接跳时结果；CPU 唤醒后时间继续增长 |
| VM 暂停         | 整个 VM 处于暂停状态时，虚拟时间停止，不能因为 active 集合为空而触发跳时 |

QEMU 支持 TB 直接链接，多个 TB 可以连续执行而不返回 C 层执行循环。因此计数和滑窗检查必须覆盖这条路径，测试中要专门构造长时间运行的纯计算循环。[QEMU Translator Internals](https://www.qemu.org/docs/master/devel/tcg.html)

测试环境采用同一份 Guest 镜像、同一份工作负载，记录 QEMU commit、启动参数与线程绑定关系。对照配置如下：

| 配置                      | 用途                                           |
| ------------------------- | ---------------------------------------------- |
| 原有 MTTCG，slowtime=1    | 复现 Host 执行能力不足引起的超时，测量原始性能 |
| 原有 MTTCG，固定 slowtime | 对照固定倍率下的超时和时间变化                 |
| 新方案，slowtime=1        | 验证指令驱动时钟与滑窗行为                     |

上游 `-icount` 与 MTTCG 不兼容。新方案运行时需要确认各 vCPU 的 Host 线程确实同时执行 Guest 代码，避免测试实际落在单线程执行模式。[QEMU MTTCG 文档](https://www.qemu.org/docs/master/devel/multi-thread-tcg.html)

使用文中的参数作为基准：

```
SIM_IPS               = 2,000,000,000
CNTFRQ                 = 62,500,000 Hz
TIME_UPDATE_INTERVAL   = 100 μs
UPDATE_ICOUNT          = 200,000
MAX_TIME_SKEW          = 1 ms
MAX_SKEW_ICOUNT        = 2,000,000
```

Host 将两个 vCPU 线程、主线程分别绑定到独立物理核。通过绑核竞争或线程定向限速降低指定 vCPU 的执行速度；另设主线程受压场景。记录实际执行速率，避免把限速配置值当成实际减速倍率。

测试日志以**全局时间更新、active 切换、滑窗等待与唤醒、跳时、Timer 到期**为记录点，包含：

```
host_monotonic_ns
event / cpu_id / wait_reason
active
raw_icount / raw_base / logical_base / logical_icount
global_icount / virtual_time_ns
timer_deadline_ns / callback_time_ns / irq_handler_time_ns
```

Host 时间用于定位线程停顿和设置测试看门狗；Guest timeout 的判定使用 Guest 时钟。日志中的多字段状态需要一致性快照，普通日志打印顺序不能充当跨线程发生顺序。

**基础计数和时钟换算**可以用小型 AArch64 裸机程序验证，控制中断与异常入口，精确计算标记区间内执行的指令数。

| 编号 | 场景与操作                                          | 通过条件                                                     |
| ---- | --------------------------------------------------- | ------------------------------------------------------------ |
| C1   | 单核执行已知指令数的汇编循环，改变循环次数          | `raw_icount` 增量与实际执行指令数一致；计入分支和约定范围内的标记指令 |
| C2   | 执行相同逻辑，分别构造短 TB、长 TB、直接链接循环    | 计数结果一致；直接链接期间计数持续更新，滑窗检查持续生效     |
| C3   | 在 TB 中间触发可控异常、MMIO 访问、中断退出         | 未执行的 TB 尾部指令不被计入，重入和重执行路径不重复计数；异常指令自身的计数口径有明确定义 |
| C4   | 两核分别执行已知指令数，记录每次协调快照            | active 集合稳定时，global 更新符合快照中各核逻辑进度的最小值，不能按各核指令数求和 |
| C5   | 单核在稳定映射、无跳时区间推进 `2,000,000` 全局指令 | 对应虚拟时间增加 `1ms`，System Counter 增加 `62,500 tick`    |
| C6   | 使用不能整除的 SIM_IPS、计数频率与长时间累计值      | 结果符合定义的整数换算与舍入规则；无乘法溢出、累计漂移或时间回退 |
| C7   | 在两核之间通过 release/acquire 握手依次读取 CNTPCT  | 后发生的读取值不小于先发生的读取值；允许两次值相等           |
| C8   | 设置已知 CNTVOFF，检查 CNTVCT 与 CNTPCT 的对应关系  | 使用同一时间样本扣除 offset 后结果一致；固定 offset 期间各核读数不回退 |

C3 必须单独验证。QEMU 原有 icount 对 MMIO 等中途退出路径包含计数修正处理，直接累加完整 TB 的指令数容易漏掉这些情况。[QEMU TCG Instruction Counting](https://www.qemu.org/docs/master/devel/tcg-icount.html)

**滑窗与线程推进**使用双核持续计算负载，避免 Guest 业务本身的阻塞影响判断。

| 编号 | 场景与操作                                             | 通过条件                                                     |
| ---- | ------------------------------------------------------ | ------------------------------------------------------------ |
| S1   | 两核执行速度接近，持续运行                             | global 持续增加；两个 vCPU 均能执行；无周期性长时间停顿      |
| S2   | 将 Core1 实际执行速度降低到原来的约 1/10、1/100        | Core0 达到窗口上限后等待；global 受 Core1 进度约束；在主线程更新globaltime之后，Core0被主线程唤醒继续执行 |
| S3   | 两核都达到当前 global 对应的窗口上限                   | 主线程仍能扫描、推进 global 并唤醒线程，无永久等待           |
| S4   | 一个核距窗口上限仅剩少量指令，下一 TB 长度超过剩余额度 | 若按严格滑窗验收，任何时刻均不超过上限；记录最大越界指令数   |
| S5   | 反复让 global 更新发生在“检查等待条件”和“真正睡眠”之间 | 无丢失唤醒；满足恢复条件的 vCPU 不会永久睡眠                 |
| S6   | vCPU 处于滑窗等待时，触发 IRQ、跨核 TLB 同步、VM stop  | 能处理必要的 QEMU 控制工作，无持锁等待导致的死锁             |
| S7   | 主线程受压或暂时延迟调度，vCPU 正常执行                | vCPU 在窗口处受限；主线程恢复后继续推进；时间无异常跳变      |

S4 按文中给出的严格不等式判定。实现为：保留 TB 结束后，检查是否CoreX额度用尽，如果用尽此时将进入yield。

**active 集合与 Idle Time Warp**重点覆盖“退出、重新加入、所有核等待”之间的切换。

| 编号 | 场景与操作                                                   | 通过条件                                                     |
| ---- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| A1   | Core1 实际进入 WFI，Core0 持续计算                           | Core1 退出同步集合，Core0 能继续推动 global                  |
| A2   | Core1 的一个 Linux task 等待 mutex，同核另一个 task 持续计算 | Core1 保持 active，继续参与最小进度计算                      |
| A3   | 分别测试 WFE 消费已有事件立即返回、WFE 实际等待              | active 状态与 vCPU 是否实际停止执行一致                      |
| A4   | Core1 WFI 期间让 global 大幅前进，再通过 IRQ 唤醒            | 重新加入时逻辑进度对齐当时 global；随后按新增 raw 指令推进，无旧进度拖住时间 |
| A5   | 高频执行 WFI/IRQ 唤醒，并让主线程同时扫描                    | 无基准混用、无异常巨大 logical 值、无时间回退                |
| A6   | 两核均在滑窗等待                                             | 不触发 Idle Time Warp                                        |
| A7   | 两核均 WFI，存在未来的虚拟 Timer                             | 时间推进至最近 deadline，原有 callback 执行并唤醒对应 CPU    |
| A8   | 两核均 WFI，设置多个 deadline 不同的 Timer                   | 先处理最近到期事件；每次跳时前重新判断是否仍然全 idle        |
| A9   | 两核均 WFI，无虚拟 Timer，随后注入外部 IRQ                   | 无凭空时间增长或忙循环；外部 IRQ 能恢复执行                  |
| A10  | 跳时、唤醒、计算、再次 WFI，循环执行                         | 时间持续单调前进；无跳时后回退，也无等待 raw 指令“追上跳时”造成的长时间冻结 |
| A11  | VM stop 后等待一段 Host 时间，再 cont                        | 暂停期间虚拟时间保持不变；恢复后连续推进                     |
| A12  | all-idle 判定附近同时发生外部 IRQ、Timer 修改或取消          | 已恢复执行的 CPU 不被遗漏；不依据失效 deadline 错误跳时      |

A10 能直接检查文中两种时间更新方式的衔接：

```
正常运行：virtual_time_ns = global_icount × 1e9 / SIM_IPS
空闲跳时：virtual_time_ns += deadline_ns
```

测试必须证明下一次正常更新时间能保留此前的跳时增量。

**Timer 测试**同时记录三个时间：设置的 deadline、QEMU callback 执行时刻、Guest IRQ handler 入口时刻。

| 场景             | 操作                                                      | 判定                                                         |
| ---------------- | --------------------------------------------------------- | ------------------------------------------------------------ |
| 持续计算期间到期 | 两核持续运行，设置一次性 Generic Timer                    | callback 不早于 deadline；最终产生 IRQ，Guest 能处理         |
| 短周期与边界     | 周期取 `10μs、100μs、1ms、10ms`，改变相对更新点的起始偏移 | 统计 callback 和 IRQ 延迟的 P50/P99/最大值，满足业务规定的容限 |
| Timer 修改       | 到期前取消、提前、推迟 deadline，设置已到期值             | 行为符合对应 Timer 语义，无旧事件残留或错误唤醒              |
| 设备 Timer       | 覆盖业务依赖的设备定时回调                                | 使用统一虚拟时间，回调能正常调度                             |
| 主线程恢复       | 延迟主线程后恢复，期间跨过多个 deadline                   | 到期事件按设备既有语义处理，无永久漏调度或回调忙循环         |

这里需要单独验收**每次虚拟时间实际增加多少**。文中的 `100μs` 尚不能直接作为 Timer 延迟上限：主线程调度延迟、一次扫描跨过多个更新粒度，以及 IRQ 投递延迟都会影响结果。

如果要求每次普通更新最多推进 `100μs`，应增加对应硬断言；否则记录实际最大步长，并使用明确的业务 Timer 容限验收。

**双核收发包测试**采用 Core0 发送请求、Core1 处理并回复。每个请求携带序号和校验值，同时检查丢包、重复包、乱序与数据错误。

先用共享内存请求/应答隔离时钟和调度问题，再在相同负载条件下覆盖实际收发包设备路径。两条路径均纳入最终验收。

| 场景             | 负载设置                                                     | 通过条件                                                     |
| ---------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 正常处理         | Core1 每包执行约 `400,000` 条固定工作指令；Guest timeout=`5ms` | 请求正常完成，结果正确                                       |
| 接收端 Host 变慢 | 固定上述 Guest 工作量，逐步降低 Core1 的 Host 执行速度       | Host 完成时间显著增加；在预留足够虚拟时间余量的条件下，无新增 Guest timeout |
| 发送端 Host 变慢 | 降低 Core0 的 Host 执行速度                                  | 无同步死锁，协议数据正确                                     |
| 实际处理工作超时 | Core1 每包工作量提高到约 `20,000,000` 条指令                 | Guest timeout 能实际触发，防止时间冻结掩盖超时               |
| 无回复           | Core0 轮询等待；Core1 保持运行但不回复                       | global 持续推进，Core0 按 Guest 时间超时                     |
| Timer 等待回复   | Core0 等待回复时进入 WFI，由 Timer 提供超时唤醒              | 有回复时正常完成；无回复时 Timer 能唤醒并触发超时            |
| 锁与共享队列     | 加入 atomic、屏障、exclusive 重试和队列竞争                  | 无数据破坏、丢更新或永久等待                                 |
| 持续及突发流量   | 改变发送速率、队列深度、处理工作量                           | 记录吞吐、积压和超时率，定位容量边界                         |

`400,000 / SIM_IPS = 200μs` 只表示固定处理指令的标定时间。整包耗时还包含调度、协议处理和设备路径，因此需要保留足够 timeout 余量。

**同样的包数和指令数不要求每次得到完全相同的完成时间**；MTTCG 的线程交错会变化。验收重点是 Host 减速没有通过时钟直接消耗 Guest 的超时预算，并且业务工作量真正超限时仍能超时。

性能测试关闭高频诊断日志，分别测量单核计算、双核独立计算、双核收发包。参数独立变化：

| 参数         | 测试取值                |
| ------------ | ----------------------- |
| 更新时间粒度 | `10μs、100μs、1ms`      |
| 最大领先时间 | `100μs、1ms、10ms`      |
| SIM_IPS      | 基准值的 `0.5、1、2` 倍 |

独立扫描更新时间粒度与 skew，可以检查二者是否确实解耦。记录：

- Host 每秒完成的 Guest 指令数、包数及固定任务完成时间。
- 两个 vCPU 线程实际并行执行的情况。
- 主线程 CPU 占用、滑窗等待次数与等待时间。
- 全局时间更新步长、Timer 延迟、最大领先指令数。
- 开启新方案相对原有 MTTCG 的性能开销。

最终验收将**计数错误、时间回退、严格滑窗越界、错误跳时、死锁、丢失唤醒、业务数据错误**设为零容忍项。性能开销和 Timer 延迟使用项目明确的门限；并发状态切换建议至少重复 `100,000` 次，真实收发包覆盖至少 `1,000,000` 次交互及一轮持续运行测试。测试超时退出时保留各线程栈、最后一次协调快照和最近的状态事件，供定位停滞原因。
