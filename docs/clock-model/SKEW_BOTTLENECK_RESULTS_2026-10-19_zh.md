# Skew 瓶颈研究：证据、候选实现与后续对策

本轮最稳定的收益来自移除纯计数器读取的 BQL 获取。发布与预算续配需要配合
考虑，但把全部选项打开并不总是最快：4 vCPU 的组合候选改善了计数器场景，
32 vCPU 超额订阅时，计数器单项的墙钟中位数更低，三轮中两轮更快。
新路径均保持默认关闭。

研究基于恢复到的 QEMU 10.2 / P2 源码：运行时基线 `760b52a`，复现入口
`ed6fd11`。未取得上一会话后期指数模型的完整源码，因此这些结论不能直接
标注为该指数模型的测试结果。

## 1. 瓶颈沿哪些路径发生

| 路径 | 代码与证据 | 判断 |
|---|---|---|
| 计数器读串行化 | `get_cp_reg64` 对 ARM_CP_IO 获取 BQL；本场景固定 524288 次 CNTVCT 读取。诊断 QSP 正好记录 524288 次该位置的 BQL 获取 | 已确认是读计数器场景的主要可消除成本 |
| 已完成的共同进度尚未发布 | 原复现的全核边界等待；`skew_update` 原先由周期回调驱动 | 已确认存在发布等待，但只加通知不能保证主线程及时运行 |
| 额度发布后的恢复成本 | 新增实际发布完成时间戳，与 `skew_wait waiting=0` 对齐 | 已确认显著；包括宿主调度、条件变量返回和重新获取进度锁 |
| 续配沿旧 grant | `skew_budget_exhausted` 原先只沿 `skew_budget_global` 续配 | 已确认有多余执行返回；减少返回次数本身不保证墙钟改善 |
| 剩余并发读和全局协调 | 可见时钟的 seqlock/CAS、O(N) 扫描、progress_lock、唤醒与调度 | 是后续候选热点；尚未用 CPU profiler 分解各自 CPU 消耗，不能给出精确占比 |

计数器快读仅放行 `gt_cnt_read` 和 `gt_virt_cnt_read`，继续调用原读函数。
共享时钟已有 seqlock/CAS 读路径，计数器偏移取自当前 vCPU 的架构状态，
模式切换先停止 vCPU。保留 ARM_CP_IO、翻译器 I/O/TB 边界和访问检查；
TVAL/CTL/CVAL、定时器写入和普通 MTTCG 继续使用原路径。

Skew 的计数器读在 BQL 内执行插值、宽整数运算和可见时间发布；协调器也
需要 BQL。读密集的 vCPU 之间、以及读取和额度发布之间，会争用同一把锁。
仅缩短周期发布等待，仍保留了这一串行化路径。

QSP 的 mutex 时间是累计获取时间，不是持锁时间，也不能直接作为墙钟占比。
第二阶段基线诊断中该读取位置获取耗时为跨线程累计 1.94944 秒；启用快读
后的对应诊断不再出现该位置。诊断开销较大，性能结论只使用无 trace/QSP 运行。

## 2. 对照设计与完整性

第一阶段：发布方式 periodic / notify / inline × 新旧预算快照，加原始
MTTCG/P2 基线，两种负载三轮，共 48 次性能运行、6 次诊断。

第二阶段：基线、计数器单项、notify 单项、notify + 计数器、inline + fresh、
inline + fresh + 计数器，共 36 次性能运行、8 次诊断。每组固定同一二进制、
每核 2097152 次循环、4 vCPU、1 ms 窗口、200M IPS、100 µs 周期。每次总计
268435456 条有效计算体指令，计数器场景另有 524288 次读。完成条件是固定
工作量与计算结果，未使用 Guest 时间决定何时结束。

规模检查：32 vCPU、每核 524288 次循环，比较基线、计数器单项与 inline
组合，三轮共 18 次性能运行。总计算体指令为 536870912，计数器读取 1048576 次。
宿主可见亲和性为 0–8，CPU quota 为 8；这是超额订阅测试。

最终采用的性能集合共 **102 次，均通过固定工作结果校验和原始 marker 回读
核验**；诊断共 14 次，哈希和等待分解均重新核验。
另保留早期小规模 pilot，其数据不计入正式结果。第二轮反转顺序，第三轮
轮换起点；记录所有运行，不挑选最快值。原始二进制、阶段一二进制均另存。

归档时发现原第二阶段和规模检查中共 4 份空原始输出，结构化测量仍在。
对这两个完整矩阵各重跑一次，替换其性能集合；原 54 次性能运行整体保留、
不纳入下表。复核版增加 fsync、哈希、回读及结果内嵌原始 marker 输出。
因此总共实际运行 156 次正式/历史性能样本，最终采用其中 102 次，未择优筛选。
复核版的 3 个独立 `qemu.log` 副本随后仍变为空文件，但采集时保存于逐次及
整组 JSON 的原始 stdout 双份副本完整，均匹配采集时的字节数和 SHA256。
这 3 次使用真实 stdout 副本重新解析 marker，核对所有测量字段；没有从
测量数字反向拼造日志。异常副本原样保留并列入完整性报告。

第一阶段有一次 notify/fresh 运行伴随 cgroup 限流计数增长，已保留并标注；
第二阶段和 32 vCPU 正式性能运行未观察到该计数增长。这不排除宿主调度噪声。
三次重复只能支持初步选择，不能证明长期尾延迟或严格性能上界。

数据位于 `build/bottleneck-20261019/`：

- `factorial/`：第一阶段全部参数、逐次结果、轨迹与 QSP。
- `counter-factorial-audited/`：第二阶段最终性能集合；原 `counter-factorial/`
  中完整的 8 次诊断仍保留使用。
- `scaling-32cpu-audited/`：最终规模检查；原 `scaling-32cpu/` 保留作历史。
- `integrity-audit.json`：最终纳入/排除清单、原始 marker、Guest 哈希、trace
  哈希和三份 QEMU 二进制哈希的核验结果。
- 每组包含 `environment.json`、预先写入的 `plan.json`、逐次 `runs.json`、
  `summary.json` 和 `paired-ratios.json`；诊断保存原始 trace 哈希和大小。

## 3. 性能结果及组合边界

以下均为固定工作计时区间的三轮中位数，不含 Linux 启动/关闭。
配对加速比先在每轮计算“该轮基线墙钟 / 该轮候选墙钟”，再取中位数。
因此不一定等于表中两个墙钟中位数相除。

| 计数器场景 | 墙钟中位数 ms | 墙钟范围 ms | CPU 秒中位数 | 配对加速比中位数（范围） |
|---|---:|---:|---:|---:|
| 4 vCPU：periodic/stale 基线 | 481.13 | 446.26–510.34 | 0.799997 | 1.00 |
| 4 vCPU：只改计数器 | 232.24 | 203.76–341.32 | 0.484153 | 1.92（1.41–2.50） |
| 4 vCPU：inline + fresh + 计数器 | 215.38 | 173.54–231.82 | 0.487646 | 2.23（1.93–2.94） |
| 32 vCPU：periodic/stale 基线 | 1506.18 | 895.20–1526.77 | 3.846137 | 1.00 |
| 32 vCPU：只改计数器 | 371.19 | 263.33–826.79 | 1.214408 | 2.41（1.85–5.72） |
| 32 vCPU：inline + fresh + 计数器 | 455.37 | 441.92–526.24 | 1.601581 | 3.35（1.70–3.41） |

4 vCPU 组合相对基线三轮均降低墙钟和 CPU 秒；配对 CPU 秒比例中位数为
0.546。有效计算体吞吐量中位数从 557.9 增至 1246.4 MIPS。收益来自相同工作
用更少资源完成，不是靠增加等待降低 CPU 使用率。

4 vCPU 组合相对“计数器单项”三轮都更快，但一轮只快约 0.2%，CPU 秒中位数
也没有进一步下降；32 vCPU 时组合有两轮更慢，墙钟和 CPU 秒中位数均更高。
因此没有证据支持将 inline/fresh 全局设为默认。32 核这一差异还需要定点
profiling 才能拆分共享锁、唤醒、扫描与宿主调度的影响。

notify + 计数器在最终 4 vCPU 集合的墙钟中位数为 301.65 ms，范围
244.40–369.08 ms，配对加速比中位数为 1.69，仍慢于计数器单项。
第一阶段 notify/fresh 还发生回退和长尾，不能把通知主线程视为低延迟发布保证。

纯计算场景仍需谨慎：最终集合 inline 组合从基线 179.62 ms 到 152.13 ms，
三轮均更快；第一阶段 inline/fresh 却出现明显回退。没有计数器读取的计算体
不会直接受益于快读选项，相关差异不能归因于移除读锁。三轮观测不足以证明
跨阶段稳定性，计数器单项也不会消除纯计算场景的窗口等待。

CPU 秒 / 墙钟表示平均占用的宿主核数，不是 Guest 指令执行占比。本次未测到
“宿主 CPU 时间中有多少百分比在执行有效 Guest 指令”；该指标需要单独的
CPU 采样分析。普通 MTTCG 未应用相同的计数器读优化，不作对称优化后的排名推断。

## 4. 为什么只改一个同步点不够

第一阶段计算诊断中，notify/fresh 的请求到发布中位延迟为 87.63 µs，
inline/fresh 为 4.37 µs；但 inline 的发布后等待仍占配置 vCPU 累计墙钟的
24.3%。这解释了为什么“发布更快”不等于同等幅度的整个任务加速。

第二阶段计数器诊断进一步显示瓶颈转移：

| 候选 | 等额度发布 / vCPU 墙钟 | 发布后至等待返回 / vCPU 墙钟 | 请求到发布中位数 µs |
|---|---:|---:|---:|
| periodic/stale | 32.3% | 9.1% | 无按需请求 |
| 只改计数器 | 38.6% | 18.2% | 无按需请求 |
| notify + 计数器 | 39.9% | 21.7% | 192.87 |
| inline + fresh + 计数器 | 40.0% | 16.7% | 5.72 |

这些是独立、有观测开销的诊断。分母随运行时间变化，比例增大不等于绝对
等待增加。发布后的区间含调度和重新获取互斥锁；inline 的边界区间还含
发布者自身执行协调器，不能统称为 futex 睡眠。

fresh 在第一阶段计数器诊断中将 `skew_run` 次数从 periodic/stale 的 2509
降低到 notify/fresh 的 1285，但正式性能未稳定改善。该计数包含启动阶段，
不是 ROI 内的严格计数。这项优化只减少部分退出/重入，保留了读锁和窗口边界。

当前 16 位槽已经能在执行循环内连续续配。扩大槽位只能减少结算/续配次数，
不能消除每次计数器读取的 BQL，也不能让未发布的共同进度变成可用额度。
更粗的结算粒度还可能延后最慢核进度可见性，所以不应把扩位作为本轮主修复。

## 5. 下一阶段改进顺序

| 优先级 | 工作 | 验收条件 |
|---|---|---|
| 1 | 收敛纯计数器无 BQL 读路径；审查各种 EL/权限/offset/别名，设计成可以对称用于普通 MTTCG 的机制 | 保留 ARM_CP_IO 与计数边界；CNTVOFF、真实定时器、模式切换和 Linux jitter 全部过关；两种规模固定工作 CPU 秒下降 |
| 2 | 缩短进度发布到继续执行的整段路径：合并重复协调、减少全局进度锁争用、减少无效唤醒；与 fresh 一起做消融对照 | 相同窗口下同时降低实际等待、CPU 秒和墙钟；32 vCPU 不依赖忙等提升吞吐 |
| 3 | 研究将指令额度发布和设备/时钟维护分开，减轻主线程/BQL 调度依赖 | 先明确 active 集合、单调全局进度、时钟元组提交和额度可见性的顺序；不能先放额度后补模型；暂停/idle/切换无丢失唤醒 |
| 4 | 对剩余计数器路径与 TB 热路径做 CPU 采样，区分宿主读钟、宽整数计算、seqlock/CAS cacheline、TB 结束、16 位续配 | 热点占比有实测依据再改；不能靠放宽窗口或少记指令获得加速 |

当前按需发布仅在所有 active 核都等待同一边界时触发；部分共同进度已可发布、
或最后一个非等待核退出 active 集合时，仍可能依赖周期回调。下一版必须先
设计可验证的进度触发条件，不能直接取消周期兜底。

还存在时钟模型层面的耦合：P2 动量历史按样本序号加权，增加按需协调会改变
单位宿主时间的采样次数和历史覆盖时长。虽然本轮没有替换插值公式，仍不能
据此承诺 jitter 不变。应让采样/反馈与实际时间区间匹配，或保持独立的固定
采样节奏，再验证最新模型；不能只以吞吐量选时钟策略。

## 6. 验证范围、失败记录与落地状态

真实 Guest 已覆盖：精确完成指令数、1/65535/65536/200000 指令窗口、100 次
暂停恢复、无定时器全 idle 与 UART 唤醒、实际定时器阈值和忙态投递。
上述 quick 分别用于阶段一 inline/fresh、阶段二 inline/fresh/快读及
notify/快读。扩展检查核对 CNTVOFF=1234，分别拖慢 CPU0/CPU1 的包应答与
真实超时，并对 inline、notify 分别检查运行中 20 次、暂停时 20 次模式转换。
公共执行预算 4 项单测、现有 CAS/动量锚点/停稳切换定向回归，以及 10 项
非法配置拒绝检查均通过；提取函数夹具的通过范围与真实 Guest 测试分别记录。

保留的失败与定向修复：

1. 构建途中出现空对象文件；保留其证据，重新编译对应对象后成功链接，未清理工作区。
2. 首次慢核插件无法加载 `g_ascii_strtoull`；修复测试入口显式链接 GLib。
   已完成的 CNTVOFF 结果保留，重新运行尚未通过的慢核检查，两核均通过。
3. 新切换测试一开始误从 UART 等待 semihosting 的 READY 输出，10 秒超时并
   回收 QEMU；修正观测通道后只重跑切换，两种发布方式均通过。
4. 原始输出失写触发上述完整矩阵替换；另有一份旧诊断的逐次 JSON 缺少末次
   派生字段，但原始 marker、核心测量、trace 和 `runs.json` 完整一致。
   等待分解已直接从原始 trace 重算核验，未补造原始输出。

没有匹配的 Linux 内核/模块，**未验证 Linux jitter、开机到关闭总耗时或
FastModel 对比**。裸机定时器与模式切换通过不能代替这些验收。现有结果也不
构成全负载最优证明。
